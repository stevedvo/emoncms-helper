# App-managed hot water

The optional **Settings → Hot water → App-managed hot water** switch defaults to off. The original schedule-2 routine remains selected until it is enabled. Both paths run every five minutes, independently of the automatic space heating switch.

## Enable for a trial

1. Wait until no hot water recharge is running.
2. On the ASHP controller, disable both hot water schedules and select economy as the ordinary hot water comfort mode. Keep the existing economy and standard start/stop temperatures and periodic temperature-increase configuration.
3. Review the new Hot water settings, then enable App-managed hot water and save.
4. Check Activity Logs for `App\Services\HotWaterControl`. The first decision either requests standard or confirms the economy baseline. Saving the form itself does not send a controller command.

The app uses PATCH parameter **47041**, economy **0**, standard/normal **1**. A write is recorded as successful only after the API returns `{"47041":"modified"}`. A fresh controller readback, when supplied, can also reconcile the current mode. The app does not edit weekly schedules in this mode.

## Start decisions

All clock times use Europe/London, including summer time. Threshold comparisons are strictly below the configured value.

The times below are defaults. **Settings → Tariff periods** edits the daily cheap/peak times, the overnight hot-water window and the early/quiet earliest start times. The latest normal daytime start is calculated as **daily peak start minus Recharge duration allowance**, inclusive. At a 16:00 peak start this is 13:00 with the default 180-minute allowance, or 14:00 with a 120-minute allowance. Dated cheap offers and saving sessions are also supported. See [tariff periods](tariff-periods.md) for their precedence and expiry. Minimum temperatures and recharge duration remain on the main operating-parameter form.

| Opportunity | Default threshold | Heating needed now or during the relevant cheap period | No heating demand expected |
| --- | --- | --- | --- |
| Overnight | 37°C | Wait until the evening Cosy window ends if it is needed for heating (default 00:00), then check until 07:00 | Check throughout 22:00–07:00 |
| First afternoon recharge, Monday–Saturday | 33°C | Check continuously from 10:00 through the calculated latest start | Check continuously from 13:00 through the calculated latest start |
| First afternoon recharge, Sunday | 37°C | Same afternoon window | Same afternoon window |
| Repeat daytime top-ups after an afternoon recharge completes | 33°C Monday–Saturday; 37°C Sunday | Any daytime check from the overnight finish through the calculated latest start | Wait until the quiet afternoon start (default 13:00), then check through the calculated latest start |
| Post-peak catch-up | 33°C Monday–Saturday; 37°C Sunday | From actual daily peak end (default 19:00), if the recharge fits before any reserved evening Cosy window | Wait until the overnight start (default 22:00), unless urgent |

All daytime starts must pass peak admission. There is no 12:00–13:00 gap: if heating is expected and the charging temperature first drops below threshold at 12:30, a recharge can start then, provided the allowance fits before peak. Without heating demand, a below-threshold reading before 13:00 waits until 13:00 and is reassessed then. A long allowance can leave no normal quiet-period opportunity if the calculated latest start is before 13:00. Unknown heating demand uses the early-start path conservatively. Saved changes to the peak start or recharge allowance change the cutoff on the next evaluation.

If the temperature drops below the normal threshold too late for a pre-peak start, it is checked again after the actual daily peak ends. For example, with a 120-minute allowance, a drop to 32.5°C at 14:05 cannot start immediately, but can request a recharge at the 19:00 check if still below 33°C and heating is expected. This post-peak catch-up remains available until the configured overnight start, including a new temperature drop later in that interval. Each below-threshold check calls the heating prediction: expected or unknown demand reserves the cheap period for heating by allowing an earlier recharge; a definite no-heating result waits until the overnight window (default 22:00). That boundary uses the overnight threshold, default 37°C. Urgent requests bypass the catch-up heating prediction and still pass the evening reservation check. An earlier afternoon recharge does not block catch-up. The existing recovery/retry delays and data checks still apply. No queued demand flag is needed: each evaluation uses the current charging temperature. The log identifies a `Post-peak recharge below ...` request or explains the wait until the overnight start.

The overnight start window includes 22:00 and ends at 07:00 exclusive. At the normal five-minute cadence, 06:55 is the last start check. When a proposed recharge would overlap the configured **evening Cosy window** (default 22:00–00:00), the app checks heating demand specifically for that window. Expected or unknown demand defers new starts and retries of unconfirmed starts, including urgent recharges. Before the evening starts the app reassesses demand on each eligible check. Once the app defers a recharge during the window, it keeps the reservation until the actual tariff finish, even if the rooms warm up meanwhile. The start and finish used for admission follow **Settings → Tariff periods → Daily tariff periods → Evening**.

If the evening is reserved, the first eligible check after it ends can request an overnight recharge. A start at 00:00 with a two-hour allowance is expected to finish at 02:00, before the 04:00 Cosy window. Later starts still go ahead if eligible, even when their estimated finish overlaps morning Cosy. An active recharge finishes naturally.

An overnight opportunity belongs to the date of its morning: Saturday at 22:00 and Sunday before 07:00 share Sunday's opportunity, including both occurrences of 01:00 when the clocks go back. A completed overnight recharge is not repeated, even if a 06:45 shower drops the temperature below the urgent threshold. The next overnight opportunity opens at 22:00 for the following morning, subject to the evening reservation. An unsuccessful request does not consume an opportunity.

For the first afternoon recharge, heating priority 30 immediately selects the early-start preference, so hot water can recharge as soon as needed rather than waiting for the afternoon cheap period. Otherwise, prediction evaluates current demand and the afternoon cheap period using the radiator's direct start threshold without hysteresis, cold-forecast additions, boost adjustments, UFH preheat targets, and uncompensated heating fallback. This matches live mode selection when NIBE is not space heating: a previous off decision cannot hide a new request at the adjusted threshold. It uses the currently available room temperatures rather than forecasting their cooling over the intervening hours. Missing prediction data also selects the early-start preference. These are earliest start times, not disjoint windows: heating demand does not block a later start at 12:30 or 13:30 if it still fits before peak.

After an afternoon recharge completes, another low temperature can request another top-up through the calculated latest daytime start, inclusive. This applies on every day, using the applicable afternoon threshold, and can happen more than once. Before the quiet afternoon start (default 13:00), a normal top-up checks heating demand: expected or unknown demand permits it, while no heating demand waits until the quiet start. Urgent requests bypass that wait. At or after the quiet start, repeat top-ups do not need a heating prediction. For example, a 12:30 drop after a 10:00 recharge may start a normal top-up if heating is needed, but waits until 13:00 otherwise. With a 120-minute allowance and a 16:00 peak, a repeat can start at 14:00 but not at 14:05. Peak admission still applies. Completion dates remain recorded for logging and recognising repeat top-ups; the afternoon completion date no longer imposes a one-recharge limit.

Shared `HeatingDemand` and `HeatingBoostSchedule` calculations keep the live target rules and prediction aligned. Prediction does not update `htgMode`, `allowLoadCompensation`, the stored radiator decision, or heating settings.

## Urgent requests and peak admission

An urgent recharge requires the **charging temperature (40014)** to be strictly below **20°C** and the **top temperature (40013)** to be strictly below **38°C** by default. Both limits are editable under **Settings → Hot water**. If the top reading is missing, invalid or at or above its limit, the app evaluates the normal recharge rules using the charging temperature. When both urgent limits are met, the app can request a recharge outside the normal windows, including during 10:00–13:00 and 19:00–22:00 when no heating is expected. Peak admission still applies. The completed overnight opportunity still prevents a second recharge within the same 22:00–07:00 window. A 30-minute recovery interval after a completed recharge prevents immediate repeated requests from delayed temperature readings. Through the calculated latest daytime start, a repeat top-up bypasses that interval if its below-threshold charging value has a source change timestamp newer than the controller's completion priority timestamp. This handles late showers, including a shower between the controller finishing and the app observing completion. Older state records fall back to the app's completion observation time. Failed-start retry delays are retained.

Every new request and retry of an unconfirmed start is checked for overlap with the actual daily tariff peak (default **16:00–19:00**) and dated saving sessions, using **Recharge duration allowance**, default **180 minutes**. This check is independent of the space heating peak offsets. A dated cheap offer removes only its own interval from the normal peak and can still enable a first recharge outside the normal quiet-start range when no heating is expected. Saving sessions may block a start earlier than the normal calculated cutoff. The current control minute is used, allowing ordinary seconds of scheduler latency at the boundary. The allowance plans admission; it is not a runtime cutoff.

Requests which cannot fit are deferred. At the actual daily peak end (default 19:00), the next control check can start a post-peak catch-up below the normal weekday/Sunday threshold when heating is expected or unknown, subject to any dated saving session. Without heating demand, normal recharges wait until the overnight start; urgency can still permit an earlier start. The post-peak opportunity includes the peak finish and excludes the overnight start; heating peak offsets do not move these boundaries. At the overnight start, the separate overnight threshold and completion rules apply. A post-peak run that continues into the overnight window still finishes naturally and retains its original afternoon opportunity; it does not consume the following morning's overnight opportunity. A running recharge always continues, even into a heating dip or the tariff peak. Starting promptly after peak aims to leave the evening cheap window available for space heating; it does not impose a deadline on the running cycle.

## Recharge lifecycle and recovery

State persists as JSON in `settings.hotWaterControl`: management ownership, last confirmed mode/time, pending write, request/start observations, completed opportunity dates, recovery time and last decision reason. `lastCompletedPriorityAt` records the source timestamp of the controller priority change used to confirm completion. `lastEvaluatedAt`, `lastPolledAt` and `lastTelemetryAt` record Unix seconds for the latest evaluation, actual API response and most recent live telemetry change. The evaluation timestamp advances even if the decision is unchanged, so the row's `updated_at` also shows continuing evaluations. A cache lock serializes overlapping control runs.

- Require valid numeric priority **49994** and charging temperature **40014** in a recent successful controller poll. myUplink timestamps can describe the last change to a value: an unchanged priority or temperature can legitimately have an old timestamp. The age check therefore applies to the actual poll and the latest change among known live telemetry points (outdoor/flow temperatures, degree minutes, evaporator temperature, priority and charging), rather than to every individual value. Both ages must be within the configured limit, default ten minutes. A recent comfort-setting change alone does not establish live telemetry. The republished priority heartbeat is never used as evidence of fresh controller data.
- Save the request and write intent before sending standard. A successful PATCH does not mean production has started.
- Wait for a priority-20 sample newer than the priority sample used to request the recharge.
- While priority is 20, never send an economy PATCH. This also protects an existing manual, periodic or rare economy recharge when the app begins observing it.
- Once production has been observed, wait for a newer non-20 priority sample, confirm economy, then mark an app-requested opportunity completed. An adopted run does not consume a normal opportunity.
- Retry failed writes on a subsequent control check without recording a false success. An ambiguous start response followed by production still requires economy confirmation afterwards.
- If an unstarted request reaches 30 minutes, restore economy and delay retries for 30 minutes. A run exceeding the configured duration plus an hour produces a warning and continues. Invalid or stale readings cause no mode writes.

Completion assumes the configured controller gives hot water exclusive priority until the recharge finishes. If this controller behaviour changes to alternating heating and hot water, completion detection must be revisited.

Activity logs record changes in decision reason, starts, completion, restoration, timeouts and errors. Identical waiting decisions are not logged every five minutes. API logs retain the underlying HTTP exchanges.

The start threshold is strictly below the configured temperature. In the first overnight trial on 25 October 2026, the API reported 37.0°C from 00:12 UTC (01:12 BST); 36.5°C first arrived at 02:02 UTC (02:02 GMT), after the original 02:00 start cutoff. A chart joining those sparse readings can suggest an earlier threshold crossing. The threshold remains strictly below 37°C by default, but the overnight start window was subsequently extended to 22:00–07:00. Replaying those readings now requests a recharge at the 02:05 check, provided the overnight opportunity has not already completed.

## Return to the original control

Prefer to change over while idle. Turn App-managed hot water off and save. If a recharge is running, the new service retains ownership until production finishes and economy is confirmed. An unstarted request is cancelled. After cleanup, it clears the old `hotWaterSet` flag and hands back to the original routine on a subsequent check. Failed cleanup or stale readings keep the handover pending.

Confirm the handover message in Activity Logs, then manually restore the original controller schedule times and comfort settings, including the original Sunday setting. The app switch does not restore or disable controller schedules.

No database migration, scheduler restart, or change to the installation's saved operating settings is needed to deploy the code. The new controls remain off until enabled through Settings.
